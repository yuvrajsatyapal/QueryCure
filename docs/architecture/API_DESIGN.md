# API Design

Status: Planned. Base path `/api/v1`. JSON is `snake_case`. Timestamps ISO 8601 UTC with `Z`. OpenAPI generated by FastAPI at `/api/v1/openapi.json`; the frontend generates TypeScript types from it (`openapi-typescript`) so contracts can't drift.

> Note: the user's global Kotlin/Micronaut API conventions (RPC-style, no path params) do not apply to this Python project; the brief requires a versioned REST API. Database, naming, and timezone conventions *do* apply.

## 1. Conventions

| Topic | Rule |
|---|---|
| Auth | Session cookie `qc_session` (HttpOnly, Secure, SameSite=Lax). Mutating requests require `X-CSRF-Token` matching cookie `qc_csrf`. |
| Authorization | Every resource scoped to the caller; foreign IDs return **404**. |
| Pagination | Cursor-based: `?limit=20&cursor=<opaque>`; response `{ "items": [...], "next_cursor": "…" | null }`. Cursor = base64 of `(created_at, id)`. Max limit 100. |
| Idempotency | `POST` that creates work accepts `Idempotency-Key` (UUID). Same key + same body → original response; same key + different body → 409. Keys retained 24 h. |
| Async work | Long operations return **202** with the created resource; progress via SSE. |
| Validation | Pydantic models; unknown fields rejected (`extra="forbid"`). |
| Versioning | URL major version; additive changes only within v1. |
| Rate limits | 429 with `Retry-After`; headers `X-RateLimit-Remaining`. |
| Body size | Requests over 6 MB are refused with 413 `PAYLOAD_TOO_LARGE` before buffering, with or without `Content-Length`. |

### Error envelope

```json
{
  "error": {
    "code": "SQL_NOT_ALLOWED",
    "message": "Only a single SELECT statement can be inspected.",
    "status": 422,
    "details": [{ "field": "query", "message": "statement type DELETE is not allowed" }],
    "request_id": "req_01J…"
  }
}
```

| HTTP | Codes (non-exhaustive) |
|---|---|
| 400 | `BAD_REQUEST`, `INVALID_PLAN_FORMAT` |
| 401 | `UNAUTHENTICATED` |
| 403 | `CSRF_FAILED`, `FEATURE_DISABLED` (e.g. Mode B on public demo), `ACCESS_DENIED` (restricted trial: no anonymous session, or an account that is not approved; ADR-0031) |
| 404 | `NOT_FOUND`, `NOT_FINALIZED` (manifest requested for an unfinalized run) |
| 409 | `INVALID_STATE` (e.g. approving a non-pending request), `IDEMPOTENCY_CONFLICT`, `APPROVAL_REQUIRED` |
| 413 | `PAYLOAD_TOO_LARGE` |
| 422 | `VALIDATION_ERROR`, `EXPERIMENT_NOT_REPLAYABLE`, `SQL_NOT_ALLOWED`, `SQL_PARSE_ERROR`, `CONNECTION_TARGET_BLOCKED`, `ROLE_TOO_PRIVILEGED`, `TARGET_PERMISSION_DENIED` (role lacks e.g. SELECT on a table), `TARGET_QUERY_ERROR` (PostgreSQL rejected the EXPLAIN, e.g. unknown table) |
| 429 | `RATE_LIMITED`, `CONCURRENCY_LIMIT` |
| 502/504 | `TARGET_UNREACHABLE`, `TARGET_TIMEOUT` |
| 503 | `SERVICE_UNAVAILABLE` (metadata DB not configured or unreachable), `CONFIGURATION_ERROR` (e.g. `QC_MASTER_KEY` missing, so credentials cannot be stored) |

Error messages never include credentials, DSNs, or raw driver errors (driver errors are mapped to codes; originals go to logs, redacted).

### Phase 5 additions (implemented)
- **Rate limits** (`api/rate_limit.py`, `domain/limits.py`): Postgres token buckets per user and per client-address hash on session creation, run creation, replays, inspection, connections and settings. 429 `RATE_LIMITED` with `Retry-After` and `X-RateLimit-Remaining`. The idempotent endpoints charge only after the key lookup, so a retry is never charged twice. `TRUSTED_PROXY_HOPS` decides whether `X-Forwarded-For` is read.
- **Uploads are no longer capabilities:** `/inspect/plan` and `/inspect/schema` record the uploader (`user_uploads`); `POST /investigations` accepts only digests the caller uploaded (otherwise the same 422 as an unknown digest).
- **BYOK:** `POST /investigations` and `/reinvestigate` use `llm.credential_id` (must be the caller's, else 404), else the caller's saved key for the configured provider, else the local server key. The demo profile has no server key: 503 `CONFIGURATION_ERROR` until the user adds one. The daily free quota is counted per credential.
- **`/me`** reports `features.github_login` and `features.google_login`. **Responses** carry `X-Content-Type-Options`, `Referrer-Policy: no-referrer`, `X-Frame-Options: DENY`, `Cache-Control: no-store`, and HSTS outside the local profile. The interactive `/docs` page exists only in the local profile; `openapi.json` stays.
- **Run history:** `RunSummary` (in `InvestigationDetail.runs` and `RunDetail`) gains `parent_run_id`, `finalized` and `replay {attempt_id, status, source_experiment_id}` for `experiment_replay` runs (one LEFT JOIN, no extra requests).

**Phase 4 (implemented).** All Phase 4 rows above are implemented and user-scoped (404 for another user's run, attempt, experiment or investigation). `GET /runs/{id}/report` returns the stored, digest-verified report JSON with its versions and the manifest digest; 404 `NOT_FINALIZED` for runs that were never sealed (all runs from before Phase 4). `report.md` appends an export footer after `<!-- qc-export-footer -->` (manifest digest, report digest, `shasum` reproduction; deleting the footer restores the stored bytes exactly). `POST /runs/{id}/replay/report` accepts `{client_schema_versions}`. `POST /experiments/{id}/replay` needs `{confirm_ddl: true}` and the per-user concurrency limit; a failed precondition is recorded as a `not_replayable` attempt and answered 422 `EXPERIMENT_NOT_REPLAYABLE` with `details[0].code` and `replay_attempt_id`. Cancelling a replay run (either endpoint) cancels its attempt. `GET /runs/{id}/plans/diff?from=&to=` accepts plan artifacts of the run with roles `input.plan`, `context.plan` or `experiment.plan`. `POST /experiments/{id}/replay` accepts `Idempotency-Key` (Phase 5, migration 0013): the key is scoped to the user and the operation; the same key and body return the original attempt (a repeated 422 for a `not_replayable` one, a 202 even when the user's run slots are now full); a different body is 409 `IDEMPOTENCY_CONFLICT` with nothing about the first request; concurrent duplicates converge on one attempt, one replay run and one job through a unique index. Without a key each confirmation is a new attempt. The web app sends one key per opened confirmation dialog.

**Phase 3 (implemented, T3.10/T3.12).**
- `sandbox_benchmark` needs `FEATURE_SANDBOX` (local default on, otherwise 403), a demo `workload_id`, the query, ≤ 5 param sets with one value per `$n` (a parameterized query may omit them only if it is one of the workload's example queries, whose sets are then used), and accepts `pre_authorize_demo_sandbox` (422 outside sandbox mode). Param sets accept `edge_case`.
- `GET /runs/{id}/candidates|approvals|experiments` and `GET /experiments/{id}` are user-scoped (404 otherwise). Experiment detail returns the stored config, environment, `ExperimentResult` and the raw blocks (integer-ns samples, plan digests). `ExperimentSummary` carries `replicate` (0 = the approved experiment) and, on replicate 0 of a noisy round, `replication` (the `ReplicationResult`: per-candidate `verified_with_noise_warning` / `verified` / `inconclusive`, the CI range across experiments, and the experiment IDs; ADR-0019).
- `POST /approvals/{id}/decision`: `approve` | `decline` | `partial` (a non-empty subset of the offered candidate ids, else 422). Only a `pending` request is decided; a repeat returns the first decision (202); an expired one is 409 `INVALID_STATE`. The transaction records the decision, adds the wait to `waiting_seconds`, moves the run `awaiting_approval → queued`, emits `approval.decided` and queues `run_resume`.

**Run errors (ADR-0026).** `RunDetail.error_code` comes with `error_message`, a fixed, user-facing reason written by QueryCure (never provider text or credentials). `MODEL_UNAVAILABLE` on a completed run means no model call produced usable output; the message lists the attempts by cause.

**`llm.model` (2026-10-17 audit).** Per-run model selection is not implemented: the worker uses `LLM_MODEL` (or the BYOK key's default model). A request carrying `llm.model` is refused with 422 `VALIDATION_ERROR` (field `llm.model`) instead of being accepted and ignored.

Implemented in T2.11. Phase 2 rules for `POST /investigations`:
- `sandbox_benchmark` → 403 `FEATURE_DISABLED` (Phase 3); `llm.credential_id` → 403 `FEATURE_DISABLED` (BYOK, Phase 5).
- A query or `plan_artifact_sha256` is required; the query is validated at creation (422 `SQL_NOT_ALLOWED` / `SQL_PARSE_ERROR`).
- `live_inspection` needs an owned connection (404 otherwise) and the query; production connections → 409 `APPROVAL_REQUIRED` until the Phase 3 approval gate.
- Referenced uploads must exist with the right kind (`plan`/`plan_analyze`, `schema_snapshot`). Uploads are content-addressed without an owner, so a digest acts as a capability: naming one requires having seen it or its content (see SECURITY §4).
- `Idempotency-Key` must be a UUID (400 otherwise). The request hash is SHA-256 over the `qc-json-v1` canonical body. Same key + same body from the same user → the original 202 response; a different body, or a key already used by another user → 409 `IDEMPOTENCY_CONFLICT` (nothing about the other request is returned). Concurrent duplicates converge on one run through the unique index.
- At most 2 active runs per user locally (1 on the demo) → 429 `CONCURRENCY_LIMIT`.
- One transaction creates the investigation, run (budget from `domain/budgets.py`), input artifacts and links (`input.query`, `input.param_sets`, `input.plan`, `input.schema`), the first event (`run.status_changed {from: null, to: queued}`) and the `run_start` job (dedupe key `run_start:<run_id>`).

`GET /runs/{id}/plans` returns each plan artifact (`input.plan`, `context.plan`) parsed into `{sha256, kind, role, plan, metrics}`, so the UI can highlight cited plan nodes without re-uploading. `GET /settings/models` returns `{provider, model, fallback_model, configured}`; `configured` says whether a key exists, never the key.

## 3. Streaming (SSE)

`GET /api/v1/runs/{run_id}/events` with `Accept: text/event-stream`. Supports `Last-Event-ID` (or `?after_seq=`; the header wins, and a non-numeric header is 400). Server replays persisted events with `seq > last`, then streams live events. Heartbeat comment every 15 s (`SSE_HEARTBEAT_SECONDS`). Stream closes after a terminal `run.status_changed`, or immediately if the run is already terminal and the client is caught up.

Live delivery (implemented in T2.3):
- Each API process holds **one** `LISTEN qc_run_events` connection (`events/hub.py`); the emitter sends `pg_notify('qc_run_events', run_id)` inside the event's transaction. One channel instead of one per run means one connection per process rather than one per open stream.
- A notification is only a wake-up. The stream always reads `investigation_events WHERE seq > last` from the table, so a lost notification (listener reconnecting, DB restart) delays an event by at most one heartbeat and never drops or reorders it. After reconnecting, the hub wakes every subscriber to re-read.
- Events become visible in `seq` order because `seq` is assigned under the run row lock, which is held until commit.
- The stream resolves the user in a short transaction of its own: yield-dependencies stay open until the response ends, which for SSE would hold an idle transaction per client.

`GET /runs/{run_id}/events/history?limit=&cursor=` returns `{items: [{run_id, seq, ts, type, payload}], next_cursor}` in `seq` order (limit ≤ 500; the opaque cursor encodes the last `seq`).

Why SSE: one-directional progress, auto-reconnect built into `EventSource`, works through HTTP proxies, cookie auth works; client→server actions (approve, cancel) are normal POSTs. WebSockets add bidirectional complexity we don't need ([ADR-0005](../engineering/adr/ADR-0005-sse-event-log.md)).

Wire format:
```
id: 42
event: hypothesis.created
data: {"run_id":"…","seq":42,"ts":"2026-10-11T12:00:03.120Z","type":"hypothesis.created","payload":{…}}
```

| Event type | Payload |
|---|---|
| `run.status_changed` | `{from, to, outcome?}` |
| `node.started` / `node.completed` | `{node, agent?, attempt, duration_ms?}` |
| `agent.summary` | `{agent, text}` (short, deterministic or LLM summary; never raw prompt) |
| `tool.started` / `tool.completed` | `{tool, agent, status, duration_ms, evidence_ids[]}` (args redacted) |
| `evidence.created` | `{evidence_ids[], kinds[]}` |
| `finding.created` | `Finding` |
| `hypothesis.created` / `hypothesis.updated` | `Hypothesis` |
| `candidate.created` | `OptimizationCandidate` (summary) |
| `approval.requested` / `approval.decided` | `ApprovalRequest` summary |
| `benchmark.progress` | `{experiment_id, state, param_set?, block?, blocks_total?, cancelled?, time_budget_reached?}` |
| `verification.completed` | `{experiment_id, candidate_key, verdict, gate, reasons[]}` |
| `budget.warning` | `{budget, used, limit}` |
| `error` | `{node, code, message, recoverable}` |
| `run.concluded` | `{final_status, outcome, stop_reason, synthesis_summary, materiality, no_action_evidence, usage, error}` — last content event, written by `finalize_run` (ADR-0022) |
| `report.ready` | `{report_url, outcome, manifest_sha256}` — lifecycle event, emitted after the events cutoff |
| `replay.status_changed` | `{replay_attempt_id, from, to, failure_code?}` — on the replay run's stream |
| `replay.compared` | `{replay_attempt_id, status, comparison_mode, pairs_summary}` (clients label results by `comparison_mode`, REPLAY_ENGINE §9.2) — on the replay run's stream, before its finalization |

## 4. Cancellation semantics

`POST /runs/{id}/cancel` sets `cancel_requested_at` and transitions `running → cancelling` (or `queued/awaiting_approval → cancelled` directly). The worker observes it at the next safe point (between nodes, between benchmark blocks) and cancels in-flight sandbox queries. Response is 202; final state arrives via SSE `run.status_changed`.

## 5. Models location

Pydantic request/response models live in `querycure/api/schemas/`, re-using domain models from `querycure/domain/` where the shape is identical. Response models never include secret fields — enforced by a test that scans response schemas for forbidden field names.
